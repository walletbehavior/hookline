## What changed

The Projects board now contains 41 ecosystem records. Eighteen researched seed profiles supply 44 source-linked deployment references, merged with the existing community records. The scope includes Clanker, Zora, Doppler, Flaunch, Pons, Angstrom, Hookr, What the Hook, Alphix, Bunni, Arrakis, EulerSwap, OpenZeppelin, Uniswap Labs, CLAUS, ENGRAM, and other hook-related projects. Inclusion is not an affiliation, endorsement, or claim that every record has a current v4 deployment.

Twelve projects have 19 explicitly selected monitoring targets. The public API separates linked deployments, configured monitoring targets, and successful observations. The shared reader system covers pinned state and selected mechanism events. CLAUS, Clanker, Pons, Zora, ENGRAM, Doppler, Angstrom, and Hookr have source-bound specialized readers; generic runtime, owner, implementation, and supported event reads serve other targets. Configuration is not activity, and activity is not a reconciled outcome.

The follow-up adds optional gas-free wallet-message sign-in, private list/settings save and load, one-use Telegram identity links, explicit revision conflicts, and device backup/clear controls. It does not create wallets or grant spending permissions. Deployed EIP-1271 accounts are bound to their original chain; ordinary EOA identities remain cross-chain.

A separate Wallets panel adds Privy login, explicit embedded EVM wallet creation, return-to-the-same-wallet access, secure SDK export, and external-wallet selection. Google and email are enabled. Telegram and Apple login are intentionally omitted; the Telegram bot and alerts remain independent. The picker only shows dashboard-enabled methods. No card, paid upgrade, sponsorship, session signer, or bot custody was added. Embedded EOAs are distinct from smart accounts and automatic order execution.

Pending approval and swap hashes survive account/chain changes in the open page. Check confirmation retries receipt verification, not submission. Native dialogs step aside for the SDK's confirmation screen. No financial transaction was executed as part of rollout testing.

CLAUS now separates pinned fee allocations, accrued balances, buyback/burn records, FOMO transfers, liquidity additions, and NFT reward events. A supported burn is marked transfer-confirmed only when the same successful receipt contains the exact matching token transfer to zero. Other events stay contract-reported, with proof status visible. ENGRAM accrued fees stay accrued. No lifetime payout totals are inferred.

Doppler monitoring now follows the canonical Airlock contracts on Base and Robinhood Chain. Source-bound launch, migration, module-state, and collection events retain their exact transaction and block. The `Create` event's `poolOrHook` field is not assumed to be a hook because the official interface also supports v3 initializers.

Angstrom monitoring now includes the official Ethereum ControllerV1 as a separate contract from its hook. Six block-pinned reads expose the bound hook, owner, fast owner, pending replacement, configured-pool count, and authorized-node count. Six source-bound event types retain pool configuration and removal, opaque batch updates, accepted controller replacements, and node-set changes. Fee fields retain their millionths denominator; they are configuration, not measured swap charges.

Hookr monitoring now follows the Hookr 1 launcher and shared root on Robinhood Chain using the exact official deployment manifest, repository commit, runtime identities, and source hashes. The two contracts each expose at most six source-bound event topics. Launch-family, member-pool, dev-buy, launch-fee, family-transfer, pool-open, hook-fee, and recapture-lane records remain distinct. In particular, quote earned/refunded and subject burned are never added together or presented as one USD fee.

What the Hook is now a researched profile with the official Robinhood hook and `$WTH` token addresses. Its mechanism remains project-described and the linked Hookr repository identifies its executor as closed source, so Hookline provides generic pinned contract observations without a source-bound event reader or verified payout claims.

Routine accrual records remain visible in Activity but do not fire payment-style notifications.

Method-specific provider fallback now verifies the same pinned block, respects rate-limit cooldown, and counts every HTTP attempt against the scan budget. It does not turn provider failure into zero activity or advance an unscanned cursor.

Projects, deployments, observations, events, and subscriptions share a schema. Each retained observation identifies its source block and probe status. Contract-event records retain transaction/log evidence. Public activity excludes orphaned records; baselines and historical catch-up do not become fresh-activity notifications.

The public activity surface now defaults to configuration changes and outcomes, with separate configuration, outcome, accrual, and backfill filters. Project profiles connect source-linked hook deployments to byte-identical runtime families and disclose the family snapshot time. Runtime identity does not establish project affiliation or equivalent configuration.

The Projects board now supports bounded two-to-four-project evidence comparisons. Selection remains visible on the board, comparison routes are shareable, and each column keeps evidence tier, deployment coverage, chain footprint, runtime coverage, source-bound reader counts, and latest block-pinned fields. Missing values remain unavailable; the view does not produce a performance or risk ranking.

Suggestions, corrections, and domain claims use private API receipts. DNS TXT proof grants metadata control only. Ordinary requests go to an authenticated agent review queue instead of an email inbox. The scheduled reviewer depends on its configured workstation being online. No payment or HKLN holding is required to submit.

The Telegram runtime adds named alert cards, full copyable contract addresses, and Details/Pause/Resume/Add alert/Projects navigation. Saved trade preferences include slippage, native-coin amounts, sell percentages, and inactive TP/SL profiles. The website has compact settings, device-local preferences, exact balance-percent sizing, and explicit wallet handoffs. No link quotes, signs, or submits on navigation.

The board's index timestamp is smaller and located below the Hook / Token / Project selector. It remains the actual snapshot-generation time, not a page-refresh clock. Dynamic-fee sentinels are displayed as Dynamic instead of misformatted percentages. Indexed-liquidity alerts require complete measurements of the same pool set.

## First-party Hook Tape

Hook profiles now surface their finalized Base PoolManager relationships directly, with exact pool IDs, configured LP fee fields, blocks, and source transactions. The same evidence can be opened as a filtered Tape view.

Telegram subscriptions now consume only the Tape's completed live window. They seed existing subscriptions silently, preserve the last complete baseline when a read is unavailable, and never promote historical backfill into a new-pool alert. A genuine new finalized relationship carries the sourced name, full hook address, pool ID, block, and copyable transaction.

- A new Tape view and public API read finalized `Initialize` logs directly from the official Uniswap v4 PoolManager on Base.
- A separate finalized live cursor reads `Swap` logs for already-resolved hooked pools. Rows retain signed pool deltas, the fee emitted by PoolManager, post-swap state, exact transaction/log evidence, and their derivation version.
- A bounded receipt pass reads at most 12 successful swap transactions per run. It retains up to 64 normalized ERC-20 transfers per transaction when they touch a saved hook or pool currency, plus transaction gas and exact receipt-block binding. Receipt flows are not labeled as fees or payouts.
- A separate bounded trace pass selects one receipt-backed successful transaction per run. It prioritizes receipts with hook-linked ERC-20 transfers, inspects at most 1,024 trace items, and retains at most 64 relevant call frames. Direct hook callbacks, swap-return deltas, valid explicit LP-fee overrides, relevant native value, and direct call-frame gas remain visibly separate from fee attribution. This coverage does not measure failed attempts or refusal rate.
- A block-window activity API and compact Tape leaders summarize retained swaps, active pools, distinct senders, and PoolManager fee ranges without presenting a partial window as complete.
- Hook profiles show the same explicit activity window. Telegram alerts compare the latest complete finalized reading for the same pool and report PoolManager fee moves of at least 10 basis points with the before/after rate, block, and source transaction.
- The Tape opens on Swaps and can switch to Pool births without leaving the evidence surface. Swap and pool pagination remain independent.
- Raw swap evidence is bounded to seven days and 200,000 rows, with at most 5,000 expired or overflow rows pruned per successful scan. Orphaned receipt and trace summaries are pruned with their swaps. These limits keep D1 growth predictable while longer-lived aggregates remain future work.
- Each record retains the pool ID, hook, currencies, configured LP fee field, tick configuration, source block/hash, transaction/hash, log index, raw log, finalized boundary, and derivation version.
- One cursor follows the newest finalized range while a second cursor backfills from PoolManager deployment block `25350988`. The public status reports both ranges and the unresolved gap instead of implying complete history.
- Scans are bounded by ranges, decoded-row budgets, RPC requests, time, and an eight-minute lease. A cursor advances only after its rows are stored. A failed provider read preserves the last good evidence and cursor.
- The initial production seed saved 85 finalized pool records across 22 hooked addresses using nine RPC requests. The scheduled ten-minute scanner has continued adding current and historical rows since that seed.
- Initialization evidence proves a relationship and configured LP fee at pool birth. Swap evidence proves the PoolManager-reported fee and pool deltas for that finalized event. Selected successful traces prove bounded call behavior and callback returns; they do not yet attribute separate hook extraction, complete recipients, failed attempts, or refusal rate.

## Operational boundaries

- The scanner rotates at most six targets per 10-minute run, with bounded RPC, event, page, time, and retention limits. Each target is not promised a fresh read every 10 minutes.
- Public RPC throttling or missing historical data can delay a read or event cursor. Last-good evidence remains available, with scan status and lag shown. A supported chain is not a provider availability guarantee.
- Community discovery snapshots are refreshed by a successful sync and release, not automatically every hour.
- Market quotes come from external market sources. The first-party swap feed is a bounded finalized live window for already-resolved hooked pools, not complete historical coverage.
- Runtime equality is not proof of common ownership, identical configuration, or a new launch.
- Pool-advertised configuration is not the fee actually extracted. Individual supported CLAUS burn transfers can be receipt-confirmed; full buyback/reward totals, generalized fee attribution, and refusal rates remain reader/Hook Tape work.
- Aggregator quotes can use other pools. Hook-specific execution is not certified merely because the market is displayed.
- Smart-wallet creation, bridging, transfers, automated limit orders, and active TP/SL are not enabled. Saved profiles grant no signing permission. Priority references do not override wallet fees.
- Trading volume and expected execution revenue do not select project evidence or rank change alerts.

This is a point-in-time rollout check, not a claim that every event cursor is current or every route can execute.

The follow-up includes worker regression checks, 46 real-SQLite project-evidence tests, 7 real-SQLite Hook Tape tests, 19 provider-pool tests, 52 account/signature tests, 24 contribution tests, 20 trading-preference tests, 10 Projects API/Telegram integration tests, 53 bot tests, and focused wallet, account, Projects, trade-preference, reader, and dynamic-fee UI suites. A real workerd transport regression also checks Cloudflare-compatible redirect rejection; Node's broader Fetch behavior does not stand in for the deployed runtime. These tests exercise permissions, private identity separation, strict signed-event decoding, bounded retention, canonical block checks, preserved reads, cursor safety, idempotent delivery, exact amounts, pending-receipt recovery, and unsupported-path rejection. Passing tests are not an audit or proof of complete market coverage.
